## 从者身份与 LLM 接口（当前策略｜调研中）

**问题**：LLM 决策层要有价值，喂给它的 `BattleState` 必须带**从者身份**，否则模型只看到匿名彩色卡，推理能力不超过现有规则。身份绑定分两种，难度天差地别：

| 绑定 | 含义 | 来源 | 难度 |
|---|---|---|---|
| **① slot → 从者身份** | 前排 1/2/3 号位是谁、职阶、几宝、技能语义 | **先验**（Chaldea `TeamFormation.on_field[position]`，战前确定） | 低 |
| **② card → owner_slot** | 某张面卡属于哪个从者 | **必须感知**（逐卡识别卡面头像，三选一） | 高 |

**LLM 价值按依赖分层**：

| LLM 决策 | 依赖 | 难度 |
|---|---|---|
| 技能/宝具/回合规划（给谁 buff、宝具顺序、换不换人） | 只需 ① | 低（先验白嫖） |
| 选卡微操（Brave、喂卡给要充能/暴击的从者） | 需 ② | 高 |

**策略结论**：
1. **① 先做、② 后置**。LLM 的主要价值（高难本难在技能/宝具编排，不在选哪张平A）只靠 ① 即可解锁。
2. **身份来源 = 先验，运行时以画面为准**：Chaldea 定「谁/几号位/几宝/技能」，感知只确认存活 / NP% / CD /（以后）owner_slot。
3. **在 `battle/core` 引入身份模型 + `TeamSnapshot`**，复用 `agent/chaldea/servant_types.py` 的 `ServantInfo`，不重造；`ServantState`/`NpCard` 挂身份引用。
4. **一次性定死喂 Decider 的结构化事实 schema**（servants[身份+np+skills] / cards[color+owner_slot+is_np] / enemies），`RuleDecider` 与未来 `LLMDecider` 共用同一 `BattleState`——LLM 只换 `decide()` 实现，视觉→文本模型切换干净。
5. **owner_slot 先留 None**，LLM 先在「身份+技能+NP」上决策；要选卡微操再补感知。

**已确认与剩余调研**：
- `ServantInfo` 当前只有身份、等级、技能等级、宝具等级、礼装和编队位置，不含完整技能效果/目标语义；仍需独立 `ServantKnowledge` 数据源。
- Chaldea 分享数据包含 `actions`，现有 `convert_actions_to_bbc_rounds()` 已能解析技能、目标、宝具与换人；下一步应直接增加 `actions → BattlePlan` 转换，避免重复手写攻略。

## 集成 / 鲁棒性轨（与 V2 并行）

无人值守连刷，多为「需截图标定」：
- **结算流程**：骨架已完成，待标定 2 处——① `coords.SETTLEMENT_CONTINUE` 继续点击点（⚠ 绝不能落在「连续出击」确认钮上）；② `战斗_结算完成` 识别节点。标完把 `coords.SETTLEMENT_CALIBRATED` 置 True。失败/撤退路径未做。
- **进场动画 >15s**：首个未知等待超时可能误判卡死，需放宽/区分。
- **开场攻略 / 关卡机制弹窗**：需「点一下继续」，当前会被当异常。
- **宝具封印可用态识别**：封印时 NP 卡出现但点不动；需感知区分可用/封印态（需封印截图）。依赖上面的「选卡后置确认」。
- **GUI 入口暴露 + TurnPlan 传参**：底层 `plan.turns` 已支持，但 GUI `option` 是预定义下拉枚举，仍无法直接编辑自由结构。优先方案是复用 Chaldea actions→BattlePlan，其次才是外部 JSON 配置文件。

- `LLMDecider`：与 `RuleDecider` 同接口，在本地生成的合法候选中做高层取舍 / 解释 / 离线复盘。
- 这才是「大模型接管」的合适时机——模型有可靠事实可推理，而非盲看截图。
