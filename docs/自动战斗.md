# MaaFgo 自动战斗技术文档

> 需求：项目目标是 FGO，基于 MaaFramework 实现战斗界面的自动化操作。

## 1. 项目定位

MaaFgo 是一款 FGO（Fate/Grand Order）自动战斗助手。它**不是**一个从零开始的图像识别战斗引擎，而是一个**编排层**——将三类异构系统组合在一起：

| 组件 | 角色 | 技术 |
| :--- | :--- | :--- |
| **MaaFramework** | 导航层 — 负责游戏界面外的所有图像识别与操作（登录、章节导航、队伍选择、吃苹果等） | JSON Pipeline + OCR + 模板匹配 |
| **BBchannel** | 战斗层 — 负责战斗界面内的自动战斗执行（技能释放、卡牌选择、宝具发动） | Python 3.6 PyInstaller 打包的独立应用，自带设备控制 |
| **Agent (Python)** | 桥接层 — MaaFramework 的自定义 Action，通过 TCP 控制 BBchannel | MaaFramework Agent Server + TCP Socket |

### 1.1 为什么不直接用 MaaFramework 做战斗？

FGO 战斗界面存在以下挑战，使得纯图像识别方案不够可靠：

- **动态卡牌**：每回合发牌随机，需要识别卡牌类型（Arts/Buster/Quick）并打分
- **技能时机**：技能释放依赖回合数、NP 值、敌方状态等动态信息
- **已有成熟方案**：BBchannel（FGO-Automata）已经实现了完整的战斗逻辑，包括卡牌识别、技能序列、换人机制等

因此，MaaFgo 的设计哲学是：**让专业的工具做专业的事**——MaaFramework 负责它擅长的 UI 导航，BBchannel 负责它擅长的战斗执行。

### 1.2 为什么不直接用 BBchannel 做导航？

BBchannel 的导航能力有限，无法处理：

- 复杂的大地图导航（27个章节，需要模板匹配定位）
- 多服务器资源差异（国服/日服）
- 限时活动的动态地图
- 登录流程、更新弹窗处理

MaaFramework 的 Pipeline 系统在这方面更灵活、更易维护。

## 3. 核心数据流

### 3.1 标准战斗流程

```
用户在 Web UI 配置任务
    │
    ▼
MaaFramework 执行 Pipeline:
    1. 登录游戏 (tasks/登录.json)
    2. 导航到目标章节 (general_navigation Action, OpenCV模板匹配)
    3. 选择关卡
    4. 选择队伍 (tasks/队伍选择.json)
    5. 进入助战/编队界面
    │
    ▼
Pipeline 到达 "执行BBC任务" 节点 (Custom Action)
    │
    ▼
Agent: ExecuteBbcTask.run()
    │
    ├─ 1. 提取参数 (team_config, run_count, apple_type, battle_type)
    ├─ 2. 启动弹窗监听线程
    ├─ 3. 确保 BBC TCP 连接 (_ensure_bbc_connected)
    │     └─ 若连接失效 → 触发 "启动bbc" Pipeline节点 → restart_bbc_and_connect()
    ├─ 4. 验证模拟器连接 (_verify_emulator_connection)
    │     └─ get_connection → 检查参数匹配 → 不匹配则重启
    ├─ 5. 配置并启动战斗 (_setup_and_start_battle)
    │     ├─ load_config (加载BBC队伍配置JSON)
    │     ├─ set_apple_type (金/银/铜/蓝苹果)
    │     ├─ set_run_times (运行次数)
    │     ├─ set_battle_type (连续出击/爬塔/自由本等)
    │     └─ start_battle (启动战斗, 带重试)
    ├─ 6. 等待战斗结束 (_wait_for_battle_end)
    │     ├─ 主线程: 30秒心跳检查 (get_status)
    │     └─ 回调线程: 处理弹窗 (助战排序/队伍错误/脚本停止)
    └─ 7. 返回结果 → Pipeline 继续执行后续节点
    │
    ▼
MaaFramework Pipeline:
    8. 战斗完成信息 → 回主界面 → 继续下一次或结束
```

### 3.2 BBC TCP 通信协议

**传输层**：TCP，`127.0.0.1:25001`（命令通道）+ `127.0.0.1:25002`（回调通道）

**消息格式**：4字节大端长度 + JSON 数据

**命令通道（Agent → BBC）**：

```json
{
  "cmd": "start_battle",
  "args": {}
}
```

**命令响应（BBC → Agent）**：

```json
{
  "success": true,
  "error": ""
}
```

**回调通道（BBC → Agent）**：

```json
{
  "event": "popup_show",
  "popup_id": "1234567890.123",
  "popup_title": "助战排序不符合",
  "popup_message": "...",
  "popup_type": "askyesno"
}
```

**支持的命令列表**：

| 命令 | 功能 | 关键参数 |
| :--- | :--- | :--- |
| `connect_mumu` | 连接 MuMu 模拟器 | path, index, pkg, app_index |
| `connect_ld` | 连接雷电模拟器 | path, index |
| `connect_adb` | ADB 直连 | ip |
| `get_connection` | 获取当前连接状态 | — |
| `load_config` | 加载 BBC 队伍配置 | filename |
| `set_apple_type` | 设置苹果类型 | apple_type (gold/silver/copper/blue) |
| `set_run_times` | 设置运行次数 | times |
| `set_battle_type` | 设置战斗类型 | battle_type (0-6 索引) |
| `start_battle` | 启动战斗 | — |
| `stop_battle` | 停止战斗 | — |
| `get_status` | 获取完整状态 | — |
| `get_ui_status` | 获取UI状态(topLabel) | — |
| `popup_response` | 响应弹窗 | popup_id, action |

## 4. DLL 注入机制

### 4.1 为什么需要注入？

BBchannel 是一个**独立的 PyInstaller 打包应用**，不提供外部控制接口。要让 Agent 控制 BBchannel，有两种方案：

1. **修改 BBchannel 源码** — 侵入性强，升级困难
2. **DLL 代理注入** — 无侵入，BBchannel 升级后只需重新提取原版 `_ctypes.pyd`

MaaFgo 选择了方案 2。

### 4.2 注入链路

```
BBchannel.exe 启动
  → Python 运行时初始化
  → import _ctypes (Python启动时自动加载)
  → 加载代理 _ctypes.pyd (我们的DLL，替换了原版)
  → PyInit__ctypes() 被调用:
      ├─ LoadLibrary("_ctypes_orig.pyd")     // 加载原版，保证ctypes正常
      ├─ 调用原版 PyInit__ctypes()            // 转发初始化
      ├─ PyRun_SimpleString(inject_code)     // 注入Python代码
      │   └─ 启动后台线程
      │       └─ import bbc_tcp_server
      │           └─ start_tcp_server()      // 启动TCP服务器
      └─ return module                        // ctypes模块正常可用
```

### 4.3 弹窗劫持

BBC TCP Server 在启动时劫持了 `tkinter.messagebox` 的所有方法：

```python
messagebox.showinfo = create_popup_wrapper('showinfo', original)
messagebox.showwarning = create_popup_wrapper('showwarning', original)
messagebox.showerror = create_popup_wrapper('showerror', original)
messagebox.askokcancel = create_popup_wrapper('askokcancel', original)
messagebox.askyesno = create_popup_wrapper('askyesno', original)
messagebox.askretrycancel = create_popup_wrapper('askretrycancel', original)
```

这样，BBchannel 原本弹出的 Tkinter 对话框被拦截，转为 TCP 消息发送给 Agent，由 Agent 决定如何响应（继续/停止/自动关闭）。

**受控弹窗列表**：

- 免责声明（自动关闭，2秒延迟）
- 自动连接失败
- 助战排序不符合（askyesno，由用户配置决定）
- 队伍配置错误（askokcancel，由用户配置决定）
- 正在结束任务（自动关闭，1秒延迟）
- 脚本停止（检查是否游戏异常）
- 其他任务运行中
- 自动关机中

## 5. BBC 队伍配置格式

BBC 使用 JSON 配置文件描述队伍和战斗策略：

```json
{
    "servant_0_name": "奥伯龙",
    "servant_1_name": "尼托克丽丝",
    "servant_2_name": "芦屋道满",
    "servant_3_name": null,
    "servant_4_name": null,
    "servant_5_name": null,
    "assistIdx": 2,
    "usedServant": [0, 1],
    "master_equip": 17,
    "round1_turn0_skill": [9, 7, 8, 1, [2, 1], [3, 1], [12, 1], [10, 1]],
    "round2_turn0_skill": [7, 8, [-2, 1]],
    "round3_turn0_skill": [10, 6]
}
```

### 5.1 技能编号规则

| 编号 | 含义 |
| :--- | :--- |
| 1-3 | 从者0 的技能 1-3 |
| 4-6 | 从者1 的技能 1-3 |
| 7-9 | 从者2 的技能 1-3 |
| 10-12 | 御主技能 1-3 |

### 5.2 技能格式

| 格式 | 含义 |
| :--- | :--- |
| `n` | 使用技能 n（不需选目标） |
| `[n, t]` | 使用技能 n 并选择己方目标 t（1-based） |
| `[13, t]` | 选择第 t 个敌方目标（1-based，在技能之前执行） |
| `[-2, backup_idx]` | 换人（backup_idx 1-based，指向替补位） |

### 5.3 战斗类型

| 索引 | 名称 | 说明 |
| :--- | :--- | :--- |
| 0 | 连续出击 | 或强化本 |
| 1 | 自动编队爬塔 | 应用操作序列设置 |
| 2 | 自动编队爬塔 | 程序自主技能宝具 |
| 3 | 幕间物语 | 部分需手动 |
| 4 | 清自由本 | 不包括2.7 |
| 5 | 类主线 | 部分情况手动 |
| 6 | 主线物语·大奥 | 部分情况手动 |

## 6. Chaldea 联动

MaaFgo 支持从 [Chaldea](https://chaldea.center) 导入队伍配置，自动转换为 BBC 格式。

### 6.1 数据流

```
Chaldea 分享链接 / ID
    │
    ▼
chaldea_client.py: API请求 + 内容解码
    ├─ V1 (ver=1): H4s前缀 → base64.b64decode → gzip → json
    └─ V2 (ver=2): G前缀 → strip G → urlsafe_b64decode → gzip → json
    │
    ▼
chaldea_converter.py: BattleShareData → BBC配置
    ├─ 解析 team.onFieldSvts + backupSvts → servant_0~5_name
    ├─ 识别助战 (supportType=friend/fixed) → assistIdx + usedServant
    ├─ mysticCodeId → master_equip (BBC SN)
    ├─ actions → roundN_turnM_skill (技能序列)
    └─ delegate.replaceMemberIndexes → [-2, backup_idx] (换人)
    │
    ▼
BBC 配置 JSON → BBchannel 战斗执行
```

### 6.2 关键映射

| Chaldea 字段 | BBC 字段 | 转换规则 |
| :--- | :--- | :--- |
| `onFieldSvts[0-2]` | `servant_0~2_name` | svtId → 名称 |
| `backupSvts[0-2]` | `servant_3~5_name` | svtId → 名称 |
| `supportType: "friend"` | `assistIdx` | 标记助战位置 |
| `mysticCodeId` | `master_equip` | ID → BBC SN 映射 |
| `actions` | `roundN_turnM_skill` | 技能序列转换 |
| `replaceMemberIndexes` | `[-2, idx+1]` | 0-based → 1-based |

## 7. 导航系统

### 7.1 通用导航 (general_navigation)

基于 OpenCV 模板匹配的大地图导航：

1. 加载章节对应的大地图模板图片
2. 截取游戏屏幕中的小地图区域并缩放
3. 使用 `TM_SQDIFF_NORMED` 算法进行模板匹配，计算当前位置
4. 判断目标关卡是否在可视区域内（多边形检测）
5. 如果不可见，计算滑动距离并执行滑动手势
6. 重复直到目标可见或达到最大迭代次数

支持 27 个章节（冬木至梅塔特洛尼俄斯）。

### 7.2 Pipeline 调度

`通用战斗调度` 节点使用 `[JumpBack]` 前缀实现状态机式的流程控制：

```json
{
    "通用战斗调度": {
        "next": [
            "[JumpBack]执行回主界面",
            "[JumpBack]执行队伍选择",
            "[JumpBack]执行章节导航",
            "[JumpBack]执行bbc战斗",
            "[JumpBack]执行战斗结束",
            "战斗完成信息"
        ]
    }
}
```

MaaFramework 会依次尝试每个子节点，匹配成功的节点执行后跳回调度节点，形成循环。

## 8. 错误处理与恢复

### 8.1 BBC 战斗重试机制

`ExecuteBbcTask` 实现了两层重试：

**外层（进程级）**：最多重试 2 次

- 检测到游戏异常（闪退/模拟器崩溃/截图失败）→ 标记 `need_restart=True`
- 重启 BBC 进程（stop_bbc → 等待3秒 → start_bbc → 等待3秒）

**内层（战斗启动级）**：最多重试 3 次

- 阵容未设置提示 → 重新触发 `start_battle` 命令

### 8.2 弹窗处理策略

| 弹窗 | 类型 | 处理方式 |
| :--- | :--- | :--- |
| 免责声明 | showinfo | 自动关闭（2秒延迟） |
| 助战排序不符合 | askyesno | 用户配置决定（继续/停止） |
| 队伍配置错误 | askokcancel | 用户配置决定（继续/停止） |
| 脚本停止 | showwarning | 检查关键词，游戏异常→重启 |
| 正在结束任务 | showwarning | 自动关闭，标记结束 |
| 其他任务运行中 | showwarning | 自动关闭，标记结束 |

### 8.3 心跳监控

战斗执行期间，主线程每 30 秒发送 `get_status` 心跳：

- BBC 无响应 → 标记错误 + `need_restart=True`
- 正常响应 → 继续等待

弹窗处理在独立的回调线程中异步进行，不阻塞心跳检查。
